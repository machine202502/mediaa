# Принципы MediaA

## Цель

Изменения должны сохранять работающий, стабильный и понятный продукт. Архитектура существует не
ради формальной чистоты, а чтобы функции были предсказуемыми, ошибки локализовались, а следующая
модель могла безопасно изменить нужную часть из небольшого контекста.

Начинать нужно с цели, реальных ограничений и наблюдаемого результата. Факты из кода, тестов и
поведения важнее предположений. Если доказательство противоречит гипотезе, менять нужно
гипотезу, а не подгонять объяснение.

## Простота должна быть достаточной

Выбирать минимальное решение, которое полностью закрывает реальный риск. Не добавлять
абстракцию, настройку, сервис или инфраструктуру без конкретного потребителя.

Простота не означает минимум строк. Сложность оправдана, если она:

- предотвращает потерю пользовательского результата;
- делает ошибочное состояние невозможным;
- отделяет реальный внешний ресурс или нестабильную платформу;
- устраняет повторяющийся механизм с несколькими потребителями;
- заметно уменьшает контекст, необходимый для безопасного изменения.

Защита редкого кейса должна быть соразмерна последствиям. Постоянный дополнительный механизм для
теоретической ситуации хуже простого локального решения. Защита от потери файла, повреждения
записи или зависания выхода при этом может быть дороже обычной ветки, потому что цена ошибки
необратима.

Нельзя упрощать систему, заменяя одну защиту более сложной координацией. Если после удаления
механизма появляются новые состояния, реестры или синхронизация, упрощение не достигнуто.

## Один владелец

У пользовательской функции должно быть одно место, которое владеет её состоянием, фоновой
работой и terminal result. Другие части получают данные через явный контракт и не хранят
параллельную копию.

Общая координация допустима только для реальной композиции функций. Общий механизм не должен
становиться вторым владельцем бизнес-состояния.

## Локальный контекст для LLM

Код в первую очередь поддерживает LLM, поэтому изменение должно помещаться в ограниченный
набор связанных модулей. Помогают:

- явные типы и контракты;
- понятные имена;
- цельные модули с одной ответственностью;
- ограниченное состояние и предсказуемые side effects;
- мало неявных соглашений;
- отсутствие двух источников истины.

Не нужно устанавливать лимиты строк или делать все модули одинаковыми. Дополнительная структура
полезна только тогда, когда уменьшает количество необходимого контекста или вероятность ошибки.

## Критическое отношение к решению

Перед реализацией проверить собственное предложение:

- какие факты подтверждены кодом, а какие предполагаются;
- есть ли более простой путь;
- что произойдёт при ошибке, отмене, повторном запуске и выходе;
- не теряется ли terminal result;
- не появляется ли скрытый глобальный владелец;
- можно ли проверить результат наблюдаемым способом.

Блокирующий дефект расширяет объём работы. Личное предпочтение оформления — нет.

## Проверки являются контрактом

Изменённое поведение должно быть подкреплено проверкой, соответствующей риску:

- unit test — для правил, преобразований и границ;
- integration test — для реального файла, FFmpeg, SQLite, watcher или другого внешнего контракта;
- UI test — для действия пользователя, состояния, Accessibility и geometry;
- snapshot — для устойчивой компоновки, которую нельзя надёжно описать только данными;
- benchmark — для latency, CPU, памяти, диска или другой стоимости, из-за которой принимается
  архитектурное решение.

Тест должен проверять наблюдаемое поведение, а не повторять реализацию. Если изменение не имеет
измеримого эффекта, оптимизация не доказана.

Проверки выполняются пропорционально изменению. Успешный неизменный прогон не повторяется.
Форматирование не считается изменением поведения.

## Документация следует за реальностью

Архитектурный документ описывает текущую систему, а не историю желаний. Ограничения содержат
причину, иначе следующая модель не сможет понять, можно ли их менять. Контекст задачи должен
быть достаточным, чтобы другая модель могла продолжить работу, не восстанавливая разговор.

Пользовательское решение важнее памяти проекта. Когда требование меняет устойчивое правило,
архитектуру или ограничение, соответствующий документ обновляется в том же изменении.
