# Правила MediaA

Правила ниже обязательны. Общие способы принимать решения находятся в
[principles.md](principles.md); архитектурные факты — в [architecture.md](architecture.md);
важные технические ограничения — в [constraints.md](constraints.md).

## Источники решений

Приоритет:

1. текущее явное указание пользователя;
2. этот файл;
3. проверенный код, тесты и наблюдаемое поведение;
4. `specs/architecture.md` и `specs/constraints.md`;
5. task-документ.

`CLAUDE.md` — только точка входа и порядок загрузки контекста, а не самостоятельный источник
правил.

Пользовательское решение окончательно. Если пользователь меняет правило, его нужно сразу
исправить в этом файле. Собственный вывод не повышается до правила без прямого указания
пользователя.

## Задачи и контекст

- Работа ведётся по одной строке [progress.md](progress.md).
- Перед началом статус меняется на `в работе`, после проверки — на `готово` или `отказ`.
- Разрешённые статусы: `ожидание`, `в работе`, `готово`, `отказ`.
- Каждая задача имеет ссылку на `specs/tasks/*.md`.
- Данные в task-документе: цель, контекст, ограничения, решение, затронутые файлы, проверка и
  материальные риски. Формат свободный и зависит от задачи.
- Task-документ должен быть достаточен другой модели. Если пользователь просит, контекст можно
  сократить, расширить или разделить на несколько файлов.
- Не считать исторический план доказательством реализации. Перед изменением сверять его с кодом.

## Синхронизация проектных знаний

- При изменении архитектуры обновлять `specs/architecture.md`.
- При появлении важного технического или продуктового ограничения обновлять
  `specs/constraints.md`.
- Не переписывать туда все ограничения из кода. Фиксировать только то, что помогает принимать
  будущие решения или предотвращает повторную ошибку.
- Не оставлять противоречия между текущим указанием, правилами, архитектурой и ограничениями.
- Документация должна оставаться простой; устаревшие сведения удаляются или сокращаются.

## Git

- Коммит создаётся только после явного разрешения пользователя для конкретной партии изменений.
- Перед коммитом обязательно выполнить форматирование и обычные тесты проекта. Агентские и
  видео-тесты в этот прогон не входят.
- Разрешение на коммит не разрешает push.
- Push, force-push, теги и pull request требуют отдельного явного разрешения.
- Перед push проверить актуальность статусов в `specs/progress.md` и успешный формат.

## Безопасность UI-проверок

- Проверять UI только в отдельной тестовой копии приложения.
- Для неё задавать отдельный `MEDIAA_DEV_LIBRARY` и уникальный `MEDIAA_INSTANCE_ID`.
- Открывать страницы через `--page=`.
- Не взаимодействовать с пользовательским экземпляром MediaA, не менять его состояние и не
  завершать его процесс.
- Не отправлять глобальные нажатия клавиш. `SendKeys` запрещён.
- `PostMessage` допустим только для собственного окна.
- Не управлять чужими окнами и не снимать их содержимое.
- Завершать только процесс, запущенный для текущей проверки, по известному PID.
- Если снимок не соответствует собственному процессу, остановиться. Не искать окно по заголовку.

## Проверка изменений

- Любое изменённое поведение покрывается проверкой соответствующего уровня.
- Для Rust сначала использовать быстрый `cargo check --workspace --lib --bins --profile
  dev-check`, затем targeted tests.
- При изменении Rust перед завершением выполнить применимые `cargo test`, Clippy и format.
- При изменении Rust Clippy запускается как `cargo clippy --workspace --all-targets`; при
  необходимости warnings запрещаются через `-- -D warnings`.
- Не повторять Rust-тесты и Clippy, если код не изменялся после последнего успешного прогона.
- Изменение только форматирования не считается изменением кода.
- Для documentation/config/script-only изменения выполнять проверку ссылок, конфигурации или
  скрипта, а не полный Rust suite.
- Нельзя объявлять работу готовой при незавершённой обязательной проверке.
- Отчёт должен разделять результат, выполненные проверки, остаточные риски и требования к
  пользователю.

## Агентские и видео-тесты

- Агентские тесты (`mediaa-agent`, `mediaa-engine`, `mediaa-queue`, `mediaa-eval`, eval- и
  live-прогоны) не входят в стандартную проверку изменений. Их запускает только пользователь
  явно; агент не должен включать их в обычный прогон.
- Видео-сценарные тесты `cargo test -p mediaa-media --test pipeline scenarios` тоже не входят в
  стандартную проверку. Их запускает только пользователь явно, через skill
  `mediaa-video-tests`.
- Исключение — если пользователь прямо попросил проверить именно агентскую подсистему или
  видео-сценарии; тогда запуск обязателен и результат нужно показать.

## Тесты и benchmark

- Проверять наблюдаемый контракт, ошибки, отмену, повторный запуск и поздний результат там, где
  они возможны.
- Реальные RecordingSession внутри одного test binary запускать последовательно через общий
  mutex.
- Locale глобален; App UI harnesses удерживают общий mutex, а предыдущий harness освобождается
  до создания следующего.
- Benchmark использовать, когда архитектурное решение зависит от latency, CPU, RSS, диска или
  другой измеримой стоимости.
- Сравнивать одинаковые fixtures и настройки, отделять cold/warm, публиковать p50/p95/max и
  размер выборки.
- Микротест не заменяет end-to-end сценарий, если решение влияет на готовность UI или сохранение
  файла.
- Долгий wall-clock сам по себе не доказывает зависание. Нужны progress, cancellation,
  liveness или подтверждённый deadline конкретного ресурса.

## UI-регрессия

- Запускать настоящие egui-экраны через `egui_kittest::Harness`.
- Использовать test-only `App` factory с `TestCatalog`: временная библиотека, фиксированные
  displays/windows/microphones и отключённые native services.
- Искать и нажимать элементы через kittest и AccessKit.
- Для визуальной регрессии использовать Windows OS, фиксированный размер и устойчивую тему.
- Baseline обновлять только после просмотра diff командой
  `UPDATE_SNAPSHOTS=true cargo test -p mediaa --lib ui_regression_snapshot`.
- Не сравнивать hover и движущиеся индикаторы.
- Общие interaction/geometry tests выполняются на всех платформах; platform-specific snapshots
  не выдаются за общий контракт.

## Код

- Нет обратной совместимости: миграций, deprecated aliases, compatibility re-exports,
  transitional shims и fallback-путей для старых настроек.
- Старые поля, locale keys, tests и документацию удалять сразу после потери потребителя.
- Предпочитать поддерживаемые crates ручной реализации.
- Сначала конкретная функция или struct. Trait добавлять для нескольких реализаций или
  необходимой подмены внешнего эффекта.
- Не добавлять DI container, общий event bus, universal repository, async runtime, plugin
  architecture или глобальное mutable state без конкретной задачи.
- Не писать комментарии в коде. Допустимы только структурно необходимые safety/tool directives.
- Точные исключения:
  - `// SAFETY: …` перед `unsafe`, `# Safety` на публичном unsafe API;
  - единственное объяснение внутри намеренно пустой или игнорируемой ветки;
  - directive для `shellcheck`, `eslint`, TypeScript, Biome, `noqa` или `type: ignore`.
- Причина lint suppression пишется в `#[allow(..., reason = "...")]` или
  `#[expect(..., reason = "...")]`.

Build, test и platform-команды находятся в [README.md](../README.md).

## Языки

- Переводы находятся в `crates/app/locales/en.toml` и `crates/app/locales/ru.toml`.
- Загрузка и список языков находятся в `crates/app/src/i18n.rs`.
- Добавление ключа требует синхронного изменения всех locale-файлов.
- Тесты проверяют совпадение ключей и отсутствие неизвестных ключей в коде.

## Project skills

- `$mediaa-audit` проводит рациональный технический аудит реализации, архитектуры,
  LLM-разработки и сборки.
- `$mediaa-complexity` ищет неоправданные защиты, абстракции и сложность жизненного цикла.
- Canonical skills находятся в `.agents/skills/`; `.claude/skills/` содержит тонкие wrappers.
- Изменять нужно canonical `SKILL.md`, не только wrapper.
- Audit skills сообщают находки и не разрешают исправления.
