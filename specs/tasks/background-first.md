# Background-first: демон + UI-процесс

## Статус

План согласован 02.11.2026. Идём в разделение на демон и UI в любом случае: приложение
проводит 99 % времени в трее и там должно потреблять минимум. Этот документ — единственный
источник плана и критериев приёмки; `specs/progress.md` хранит статусы по задачам.

Отложенные решения (бэкенд, агент без UI-хоста, детали миниатюр) вынесены в
[deferred.md](deferred.md): там суть, варианты и что проверить при возврате.

## Цель

Фоновый процесс MediaA (демон) работает без графики: трей, горячие клавиши, запись, снимки,
индекс библиотеки, очередь агента, настройки. UI-процесс создаётся по требованию пользователя,
показывает состояние и завершается при закрытии окна. Время отклика пикера региона не должно
деградировать заметно для пользователя.

## Решения пользователя

- Идём в сплит всегда, без порога «если не уложимся».
- Prewarm overlay-viewport остаётся (он в UI-процессе и исчезает вместе с ним); ленивое создание
  не делаем.
- IPC — готовый кроссплатформенный пакет, а не своя абстракция: кандидат `interprocess` 2.4.7
  (named pipes в Windows, Unix domain sockets, синхронный, без async runtime).
- Пикер региона остаётся в UI-процессе.
- Уведомления эфемерные: короткий буфер в демоне, без сохранения на диск; без подключённого UI
  события теряются.
- Живой вывод (посимвольная/порционная печать) остаётся, но как поле `live_text` в снапшоте
  задачи: без отдельного канала и без «догоняния» после переподключения.
- Статусы и прогресс UI показывает реальные, опрос снапшотов 200–500 мс.
- Жизненный цикл: закрыл окно — UI завершился; упал демон — UI завершился и **не** перезапускает
  демон.
- Эталонный замер в репозиторий не коммитим: цифры зависят от машины, каждый меряет сам.
  Контрольные точки `MEDIAA_AUDIT` добавляем для разбора «из чего состоит».
- Бэкенд отрисовки сначала проверяем замерами и функциональными сценариями, потом фиксируем.
- Выключенная опция «свернуть в трей» означает принудительное закрытие: активные задачи не
  блокируют выход, фоновая работа останавливается, а незавершённая запись восстанавливается
  recovery при следующем старте. Включённая опция оставляет приложение в фоне (в сплите UI
  завершается, демон с треем остаётся).

## Целевая архитектура

### Роли

- **Демон** (`mediaa.exe --daemon`): single-instance, трей, глобальные горячие клавиши, настройки
  (`SettingsWriter`), запись (capture, finalize, recovery), конвертация, индекс библиотеки и
  watcher, очередь агента, эфемерные уведомления, лог.
- **UI** (`mediaa.exe --ui`): eframe-окно, страницы, шрифты, миниатюры, hover-превью, пикер
  региона, диалоги сохранения. Состояния не хранит; получает снапшоты, отправляет команды.
- **Лаунчер** (`mediaa.exe` без аргументов): активирует работающий демон и открывает UI; если
  демона нет — запускает его.

### Владение состоянием

| Состояние | Владелец |
|---|---|
| настройки, профили, тема, язык | демон (файл), UI получает снимок и шлёт изменения |
| запись и recovery | демон |
| capture и оверлей | UI (нужно скрыть окно и показать кадр) |
| watcher библиотеки | демон (SPLIT-4.4a) |
| индекс библиотеки | демон (SPLIT-4.4b); UI только читает и перезагружает |
| миниатюры, hover-превью, текстуры, шрифты | UI (эфемерно) |
| очередь агента, `.ai/queue.db`, модель/эмбеддинги | демон |
| выделение в библиотеке, текущая страница, скролл | UI (эфемерно, в командах — явные пути) |
| уведомления | демон (ring с TTL), UI рисует |
| прогресс и статусы | демон (снапшоты), UI только отображает |

### IPC

- Транспорт: `interprocess` в `crates/app/src/adapters/ipc.rs`; имя канала учитывает
  `core::dev::instance_scope()`, чтобы dev-копии не пересекались. На Unix — сокет с правами
  0600; на Windows — pipe с ACL текущего пользователя.
- Протокол: версия в handshake; сообщения с длиной и JSON-полезной нагрузкой в стиле
  `logic`-типов, без egui. Официальные типы: `Hello`, `Snapshot`, `Command`, `Event`, `Ack`,
  `Error`.
- Снапшоты (демон → UI, по подключению и по изменению, не чаще 5 раз в секунду): запись
  (`phase`, время, пауза), конвертация (очередь, текущий файл, процент), очередь агента
  (задачи, стадии, ошибки), `live_text` активной задачи (лимит 200 КБ), уведомления (ring),
  доступность трея/хоткеев.
- Команды (UI → демон): запись start/stop/pause/cancel, снимок fullscreen/area/window, открыть
  пикер, правка настроек, установка хоткеев, агент enqueue/cancel/continue, конвертация
  enqueue/cancel, обновление каталогов, reveal, quit UI.
- Ошибка транспорта или EOF = смерть демона: UI немедленно завершается, переподключений и
  автостарта демона нет.
- UI не берёт single-instance блокировку демона и не запускает демон (кроме лаунчера).

### Прогресс и живой вывод

- Один механизм: снапшот задачи содержит `status`, `stage`, `progress`, `error`, `live_text`.
- `live_text` эфемерен: после завершения задачи читается результат из хранилища; при закрытом
  окне не копится, лимит на размер.
- Период опроса 200–500 мс; UI перерисовывается только при изменении снапшота.

### Логи и ошибки

- Два файла: `mediaa.log` (демон) и `mediaa-ui.log` (UI); общая ротация не должна создавать
  гонку.
- Ошибка без подключённого UI (например, recovery) попадает в «последняя ошибка» и показывается
  при следующем открытии, не превращаясь в постоянную очередь уведомлений.
- Несовпадение версии протокола: UI показывает понятную ошибку и завершается, а не падает.

### SPLIT-4.4b: план переноса индекса

Демон становится единственным писателем `LibraryIndex`: загрузка, скан, `apply_scan`,
`refresh_paths`, `flush`. UI перестаёт сканировать и писать, получает `LibraryChanged` и
перезагружает индекс только для чтения (`LibraryIndex::load`). Детали миниатюр
(`set_details`) и очистка (`flush`) переезжают в команды демону; пока UI может писать только
детали, чтобы не потерять длительности. Тесты сохраняют локальный скан через `cfg(test)`.
Порядок: daemon-скан + UI reload-only → детали/удаление через демон → снять локальный скан.

Порядок: PERF-7 → SPLIT-1 → SPLIT-2 → SPLIT-3 → SPLIT-4 → SPLIT-5 → SPLIT-6 → SPLIT-7 →
SPLIT-8 → SPLIT-9 → SPLIT-10 → SPLIT-11 → SPLIT-12 → SPLIT-13. Каждая задача меняет статус в
`progress.md` на `в работе` перед началом и на `готово` после проверки.

### Задержка пикера региона (SPLIT-9a)

`scripts/windows/checks/measure-picker.ps1`, тёплый демон, GL, 6–8 прогонов:

| Сборка | до оптимизаций p50 | после p50 | p95 после |
|---|---:|---:|---:|
| release | 1529 ms | 1115 ms | 1163 ms |
| debug | 1490 ms | 1159 ms | 1242 ms |

Что убрано из холодного старта в режиме пикера: инициализация FFmpeg (~0.4 с, пикеру не нужна),
ожидание скрытия главного окна (300 мс — окно и так невидимо), загрузка индекса библиотеки,
recovery, прогрев шрифтов, стартовая уборка и перечисление окон/микрофонов. Осталось:
инициализация wgpu/окна (~0.4 с) и первый захват с показом оверлея (~0.35 с).

### Маска холодного старта (SPLIT-9b)

Демон создаёт при старте скрытое layered-окно «MediaA picker mask» на весь виртуальный экран
(чёрный, alpha 110, topmost, click-through, без активации) и показывает его мгновенно по
команде пикера из трея/хоткея или по `PickerStarting` от лаунчера. UI, показав оверлей,
отправляет `PickerShown`; демон прячет маску. Страховки: таймаут 6 с, обрыв связи с UI.

| Сценарий (debug, GL, тёплый демон) | p50 | p95 |
|---|---:|---:|
| маска видна | **62 ms** | 67 ms |
| полный оверлей виден | 1179 ms | 1194 ms |

То есть визуальный отклик на нажатие — около 60 мс, а полноценный оверлей приходит примерно
через 1.2 с и заменяет затемнение. Демон с окном маски остаётся в тех же 12 MB private и 0 % CPU.

### Функциональные проверки бэкенда (02.11.26, debug)

- GL: главное окно рисуется корректно (проверено снимком экрана: страница «О программе»,
  шрифты, иконки, вёрстка).
- Пикер области на GL и Vulkan: окно `MediaA area picker` создаётся, видимо, размер
  3200×2000 совпадает с монитором. Снимок экрана его не показывает — окно исключено из
  захвата по дизайну (защита от попадания пикера в кадр), поэтому визуальная приёмка — за
  пользователем.
- Автоматическая проверка ввода в пикер (PostMessage Esc / WM_CLOSE) оказалась
  неинформативной: окно не закрывается ни на одном бэкенде, поведение требует отдельного
  разбора и не является различием бэкендов.
- Предупреждение `Transparent window was requested, but the active wgpu surface does not
  support a CompositeAlphaMode with transparency` появляется на обоих бэкендах — это
  существующее ограничение драйвера, не регрессия GL.
- Вывод для выбора: GL даёт −90…−130 MB и 0 % CPU вместо занятого ядра; функционально главное
  окно проверено. Кандидат политики: GL по умолчанию на Windows с fallback на Vulkan при
  ошибке инициализации и настройкой выбора. Решение требует визуальной проверки пикера
  пользователем.

- 02.11.26, fix tray: команда из трея терялась. Демон отправлял `TrayCommand` новому UI до

## Риски

- Проверяется только Windows; Linux/macOS-ветки не тестируются обычным прогоном.
- Задержка холодного старта пикера (0,5–0,8 с) может потребовать маски или нативного выделения.
- Два процесса делят один exe: обновление exe при живом демоне требует проверки версии протокола.
- TCP-подобные ловушки не применяются: канал локальный, без сети.

- Замеры: до/после каждого этапа, таблица в этом документе.
