# Простой MediaA: память и периодическая нагрузка CPU

## Статус

Исследование выполнено 02.11.2026. Код не менялся: собран только ответ «из чего состоит
простой», чтобы будущие правки опирались на замеры, а не на догадки.

## Вопрос

Пользователь видел у работающей без действий MediaA около 440 MB памяти и периодические ~4 %
CPU. Отдельно важно было понять, не артефакт ли это отладочной сборки.

## Условия замеров

- Windows 11, Ryzen AI 9 H 365 (10 ядер / 20 логических), AMD Radeon 880M, один монитор
  3200×2000 при scale 2,0.
- Сборки: `cargo build -p mediaa` (debug) и `--release`; отдельно пустое приложение
  `eframe::run_native` без кода MediaA.
- Библиотека пользователя: 380 файлов, 135 MB; для изоляции — пустая библиотека через
  `MEDIAA_DEV_LIBRARY`.
- CPU считался по `TotalProcessorTime` процесса (100 % = одно ядро), память — private bytes.
- `WGPU_BACKEND=gl|dx12|vulkan` выбирал бэкенд wgpu.

## Измерения

### Пустое окно eframe (без кода MediaA)

| Сборка | Бэкенд | private | CPU |
|---|---:|---:|---:|
| debug | Vulkan | 440 MB | ~100 % одного ядра |
| debug | DX12 | 511 MB | ~100 % |
| debug | GL | 170 MB | 0 % |
| release | Vulkan | 418–430 MB | ~100 % |
| release | DX12 | 356 MB | ~100 % |
| release | GL | 137–168 MB | 0 % |

Пустое окно wgpu-бэкенда держит 4–5 % в диспетчере задач (одно ядро из 20) и сотни мегабайт
без единой строки логики MediaA.

### MediaA release, GL, пустая библиотека

Замеры по `K32GetProcessMemoryInfo` в контрольных точках старта:

| Точка | private | Прирост |
|---|---:|---:|
| старт процесса | 11 MB | — |
| перед `run_native` | 12 MB | +1 MB |
| начало `App::new` (окно и wgpu уже созданы) | 174 MB | +162 MB |
| конец `App::new` | 177 MB | +3 MB |
| первый кадр | 181 MB | +4 MB |
| после `xcap::Window::all()` | 193 MB | +12 MB |
| после создания скрытого overlay viewport | 320 MB | +127 MB |
| первый кадр overlay viewport | 336 MB | +16 MB |
| установившийся простой (внешний замер) | 382 MB | +46 MB |

Состав прироста после `App::new`:

- ~162 MB — `eframe`/`egui-wgpu`: окно, surface, swapchain и внутренние буферы рендера;
- ~127 MB — скрытый prewarm viewport выбора области: он создаётся на первом кадре под полный
  монитор 3200×2000 (физический размер surface 3200×2000), даже если выбор области никогда не
  открывали;
- ~13 MB — `mediaa_render::annotate::fonts()` держит данные 17 системных шрифтов (11 MB) до конца
  процесса; `fontdb` маппит файлы, поэтому само сканирование шрифтов дешёвое;
- ~12–15 MB — перечисление окон `xcap::Window::all()` в catalog job;
- остальное — атлас шрифтов egui, каталоги мониторов и микрофонов, буферы overlay.

### MediaA release, GL, библиотека пользователя (380 файлов)

442 MB установившегося простоя, то есть библиотека добавляет около 60 MB (текстуры миниатюр и
служебные буферы), а не основную часть.

### MediaA и бэкенд

- GL: простой ~0,5 % одного ядра, память 382–442 MB.
- Vulkan (выбирается по умолчанию как первый адаптер): 462–465 MB и поток внутри
  `amdvlk64.dll` на 100 % одного ядра больше трёх минут; за пять минут приложение отрисовало
  считаные кадры.
- Debug-прогон на Vulkan после прогрева один раз опустился до 0,08 % CPU за 120 с. Значит,
  поведение драйвера нестабильно, и «одно ядро постоянно» нельзя объяснить логикой приложения.

### Собственная периодическая работа MediaA

- `RESCAN_EVERY = 60 s`: фоновая пересборка каталога библиотеки. Для 380 файлов — единицы
  миллисекунд; для десятков тысяч файлов — 150–190 ms (см. `performance.md`).
- После старта догружаются миниатюры (первые 120 записей) и preview-прокси через FFmpeg.
- Уведомления и индикаторы анимируются только пока видимы; запись просит перерисовку раз в 100 ms.

## Выводы

1. 440 MB — не отладочная сборка: release на том же бэкенде и с той же библиотекой показывает
   те же 440–465 MB.
2. Больше половины памяти не принадлежит данным MediaA: это стек графики (162 MB до первого
   кадра), скрытый overlay viewport (127 MB) и шрифты (13 MB).
3. ~4 % CPU в диспетчере задач на 20 логических процессорах — это одно полностью занятое ядро.
   На этой машине его занимает поток драйвера AMD (`amdvlk64.dll`) на Vulkan-бэкенде; то же
   самое воспроизводится пустым окном eframe без кода MediaA. На GL бэкенде простой — 0,5 %.
4. Периодические всплески собственного кода — rescan раз в 60 с и догрузка миниатюр/preview; для
   текущей библиотеки они малы.

## Что проверить до правок

- Запустить `WGPU_BACKEND=gl` и сравнить простой: если память падает до ~380–440 MB, а CPU до
  долей процента, причина — Vulkan-драйвер, а не логика MediaA.
- Скрытый overlay viewport стоит ~127 MB на дисплее 3200×2000. Lazy-создание viewport при
  открытии выбора области или меньший prewarm-размер вернут заметную часть памяти; это
  продуктовое решение, потому что prewarm убирает артефакты первого показа.
- Выбор бэкенда wgpu (GL/DX12) на Windows — отдельное решение: DX12 на этой машине тоже держит
  одно ядро, GL держит ноль.

## Проверки

Измерения выполнены внешними счётчиками процесса; временная инструментация в исходниках снята,
рабочее дерево после исследования чистое. Функциональные тесты не запускались, потому что
поведение продукта не менялось.
