# Отложенные вопросы

Статус: ждут возврата после отладки приложения (tray, запись региона, запуск). Дата: 02.11.26.

Здесь несколько решений, которые мы сознательно не доделали. В отличие от `progress.md`, тут описана
суть: что сейчас работает, что именно не решено и как это проверить при возврате.

## 1. PERF-8 — политика бэкенда отрисовки (GL / Vulkan)

**Суть.** На этой машине (AMD Radeon 880M) Vulkan/DX12 даёт ~475 MB private и ~100 % CPU
(занятое ядро драйвером), GL — ~387 MB и 0 %. Нужно решить, какой бэкенд ставить по умолчанию и
что делать при ошибке инициализации.

**Что сейчас.** Приложение использует бэкенд wgpu по умолчанию; GL включается только вручную
через `WGPU_BACKEND=gl`. Политика не зафиксирована, настройки выбора бэкенда нет. Главное окно на
GL проверено снимком; пикер на GL создаётся, но **визуально не принят** — окно исключено из
захвата, поэтому скриншот его не показывает.

**Что нужно решить.**
- делать ли GL бэкендом по умолчанию на Windows;
- нужен ли fallback на Vulkan при ошибке инициализации GL;
- нужна ли пользователю настройка выбора бэкенда.

**Что сделать при возврате.**
1. Запустить приложение с `WGPU_BACKEND=gl`.
2. Открыть пикер области и посмотреть глазами: затемнение, рамку выделения, курсор,
   перетаскивание, артефакты, мерцание.
3. Если ок — реализовать «GL по умолчанию + fallback + настройка».
4. Если нет — оставить текущий бэкенд и разбираться с GL отдельно.

**Где смотреть.** [background-first.md](background-first.md) — раздел «Функциональные проверки
бэкенда» (~строка 205) и [performance.md](performance.md) — замеры.

## 2. Агент без UI-хоста (SPLIT-7b)

**Суть.** Сейчас `AgentHost` живёт в UI, пока окно открыто. Когда UI закрыт, демон через 5 с
поднимает свой `AgentHost` и продолжает очередь (handoff). Задачи после закрытия окна не
теряются, результат остаётся в очереди/БД.

**Что не перенесено.** «Живой» текст и `Streams`/`Feed` — это in-memory структуры UI. Пока окно
открыто, они локальны. Если закрыть окно посреди задачи и открыть снова, задача продолжится, но
live-стриминг может не показаться до завершения; итог будет в истории.

**Что нужно решить.**
- оставить handoff (проще, уже работает и проверен логом
  `agent host: handed off to daemon`);
- или сделать «агент всегда в демоне»: тогда `Live`/события нужно сериализовать и гонять по IPC,
  а сервисы очереди в UI станут прокси.

**Почему отложено.** `Live`/`Timeline`/`Event` не полностью serde; нужен отдельный
сериализуемый снимок и прокси `Scheduler`/`Streams`/`Feed`. Это отдельный крупный этап, не
блокирующий текущую отладку.

**Что проверить при возврате.**
1. Запустить реальную задачу агента.
2. Закрыть окно, подождать, открыть снова.
3. Убедиться, что результат на месте; понять, критичен ли live-текст после переоткрытия.

**Где смотреть.** [background-first.md](background-first.md) — SPLIT-7a и запись в журнале;
[architecture.md](../architecture.md) — раздел про роли и handoff.

## 3. Детали миниатюр: один писатель индекса

**Суть.** Индекс библиотеки пишет только демон — это правило зафиксировано. Но UI, когда строит
миниатюру, вычисляет детали (длительность/размеры) и вызывает `set_details` + `flush_details`,
то есть **UI всё ещё пишет в ту же SQLite**. Формально это исключение из правила «один писатель».

**Риск.** Демон делает `flush` индекса, UI — `flush_details`. SQLite их сериализует, но при
активной библиотеке и записи возможны блокировки (`database is locked`) и лишняя конкуренция.

**Что нужно решить.**
- добавить IPC-команду `SetDetails` (путь + детали), чтобы писал только демон;
- или оставить как временное исключение.

**Рекомендация.** Перенести: это небольшая команда, после неё правило снова чистое.

**Что проверить при возврате.** Открыть библиотеку с большим числом файлов, одновременно
запустить запись/скан и посмотреть логи на `database is locked`.

**Где смотреть.** [constraints.md](../constraints.md) — правило единственного писателя;
`LibraryController::set_details` / `flush_details` в `crates/app/src/logic/library/mod.rs`.

## 4. Настройки потоков и энкодеров (ENC-3)

**Суть.** Пользовательских настроек потоков, lookahead, пресетов и выбора
энкодера нет. В коде уже есть `EncoderTuning` (`zerolatency`, `threads`,
`lookahead`) в `RecordSettings`, но он применяется только к capture-энкодеру
и не выведен в UI. Финализация GIF/WebP имеет отдельный параметр threads,
который сейчас всегда `None`.

**Что отложено.** Настройки, влияющие на память/скорость/размер:
- потоки x264 на записи MP4/MKV и lossless scratch;
- lookahead/B-кадры и `zerolatency`;
- пресет x264;
- потоки декодера/финализатора GIF и WebP.

**Что важно помнить.** Потоки не меняют качество сами по себе; на захвате слишком
малое число потоков может привести к пропуску слотов кадров. GIF two-pass (палитра)
уже сделан и не требует потоков; это отдельная оптимизация.

**Подробности.** Полный разбор кода, замеров, будущей модели настроек, UI,
тестовой матрицы и открытых вопросов — в
[encoder-settings.md](encoder-settings.md). Это документ для следующего
исполнителя; здесь не дублировать.
