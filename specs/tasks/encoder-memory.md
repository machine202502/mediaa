# Память при записи видео

Статус: готово (02.11.26). Задача — убрать ~900 MB RSS у процесса записи.

## Причина

Память не течёт через IPC: кадры в UI не передаются, демон пишет локально, UI получает
только состояние и события. Основной потребитель — libx264 с автоматическим числом потоков
и lookahead: на 20-ядерной машине он держит десятки буферов кадров, и RSS растёт
пропорционально площади кадра.

Замеры (синтетическая запись MP4 30 fps, 12 с):

| Разрешение | Пик RSS |
|---|---:|
| 1920×1080 | 794 MB |
| 1280×720 | 341 MB |
| 960×540 | 209 MB |
| 640×360 | 131 MB |
| 3840×2160 | 2707 MB |

Для сравнения чистый `ffmpeg` на 1080p: авто-потоки 742 MB, `-threads 4` 232 MB,
`-tune zerolatency` 62 MB. То есть рекордер добавляет лишь десятки MB поверх энкодера.

## Решение

Добавлен `EncoderTuning` (`mediaa_core::settings`, реэкспорт в `mediaa_media::recorder`):

```text
zerolatency: bool = true
threads: Option<u32> = None
lookahead: Option<u32> = None
```

- по умолчанию `zerolatency = true`; для видео/анимаций к scratch-энкодеру применяется
  `-tune zerolatency`;
- `threads`/`lookahead` можно включить позже (в том числе из пользовательских настроек);
  при `zerolatency = true` lookahead игнорируется;
- настройка хранится в `RecordSettings.encoder_tuning` и передаётся в `RecordingRequest`.

Проверка на том же синтетическом 1080p: пик **102 MB** вместо 794 MB.

## GIF: two-pass палитра

Однопроходная схема `split → palettegen → paletteuse` заставляла `paletteuse` ждать
палитру до EOF и накапливать кадры. `mediaa_gif::encode` переведён на two-pass:
сначала `palettegen` в отдельный PNG, затем `paletteuse` потоком. Исходник по-прежнему
сначала пишется в scratch-файл, затем читается дважды — путь через файл сохранён.

Замеры (тот же паттерн, GIF, Sierra2, 256 цветов):

| Разрешение | Было | Стало | Размер файла |
|---|---:|---:|---:|
| 854×480, 30 fps | 251 MB | **78 MB** | без изменений |
| 1920×1080, 30 fps | 1012 MB | **491 MB** | без изменений |
| 3840×2160, 30 fps | 2140 MB | **1074 MB** | без изменений |
| 1920×1080, 15 fps | 682 MB | **384 MB** | без изменений |
| 854×480, 15 fps | 37 MB | 37 MB (one-pass) | без изменений |

Оставшаяся память — в основном декодер scratch-файла с авто-потоками; потоки пока не
ограничиваем по решению от 02.11.26. Время финализации выросло примерно на 5–10 % из-за
второго прохода.

Выбор автоматический: при оценке накопления кадров ≤128 MiB остаётся one-pass (для коротких
480p/15 GIF это дешевле), иначе two-pass. Дополнительно capture loop больше не клонирует кадр, если его размер уже совпадает
с размером источника: минус одна полная копия кадра на каждом захвате.

Threads/lookahead и пресеты остаются только в коде (`EncoderTuning`), без UI и без
пользовательских переключателей — как и решено.
