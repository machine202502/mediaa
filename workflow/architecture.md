# Практическая архитектура MediaA

26.10.2026. Статус: обязательные этапы E1–E7 реализованы; условные E8/E9 не выполнялись без предусмотренных планом доказательств. Документ подготовлен по запросу пользователя и не заменяет `CLAUDE.md` и пользовательские правила. Последовательность перехода — в [плане](plans/practical-simplification-plan.md).

## Текущее состояние миграции

Выполнены E1–E7: conversion, recording, capture и library имеют контроллеры в `features/`; `jobs.rs` владеет one-shot handles; глобальный `TaskSupervisor`, `TaskId`, `TaskKind`, completed history и `ActiveTasks` удалены. Clipboard и settings writer перенесены в `services/`. Feature UI возвращает локальные действия, а page-shell и `App` выполняют межфункциональную навигацию и внешние эффекты.

Условные E8/E9 и гипотезы H1–H7 остаются отдельными задачами. Отсутствие этих этапов не означает, что текущий WebP retry/budget или storage model следует удалить.

## Основной принцип

MediaA — модульное desktop-приложение. Каждая пользовательская функция имеет одного владельца состояния и фоновой работы. `App` связывает функции с жизненным циклом окна, треем и настройками. Библиотечные крейты предоставляют конкретные операции и типы; они не знают о страницах интерфейса.

У изменения обычно есть один основной модуль: например, конвертация меняется в conversion, а не одновременно в странице, общем реестре задач, отдельном сервисе, таблице занятости и диспетчере. Дополнительный тип или слой нужен, только если устраняет повторяющийся механизм либо отделяет реальный внешний ресурс.

## Границы крейтов

Сохранить существующие семь крейтов. Стрелка в таблице означает обычную production-зависимость; test/example зависимости могут отличаться.

| Крейт | Содержимое и ответственность | Зависимости внутри workspace |
|---|---|---|
| `core` | Общие типы, форматы, геометрия, настройки и их валидация, clock/pacing, source-контракты, naming/paths, атомарная публикация | Нет |
| `platform` | OS capture/audio/clipboard/window/files/single-instance; native handles и платформенные различия | `core` |
| `media` | Запись, финализация, recovery, encode/convert/probe/preview; FFmpeg adapters | `core`, `webp-pipeline` |
| `webp-pipeline` | Планирование и выполнение сегментов WebP, корректность merge, расчёт параллельности | `core` |
| `storage` | Индекс библиотеки, watcher, SQLite/cache, thumbnails на диске, сохранение screenshot | `core` |
| `render` | Аннотации и геометрия overlay, raster rendering и шрифты | `core` |
| `app` | Владельцы пользовательских функций, egui, shell, tray/hotkey dispatch и композиция зависимостей | Все перечисленные крейты по реальной потребности |

`core` здесь — общий фундамент, а не строго чистая domain-модель. Переносить Settings I/O, AtomicFile или пути в новый крейт только ради теоретической чистоты не требуется. Запрещать любую файловую функцию в core было бы дороже её текущей пользы. Новые OS API и FFmpeg-зависимости туда не добавлять.

`FrameSource`, `AudioSource` и `SourceFactory` сохраняются: они отделяют реальные OS-источники от media и позволяют проверять запись синтетическими данными. Не добавлять trait для каждого одиночного сервиса. Сначала конкретная функция или struct; trait оправдан несколькими реализациями или необходимой подменой внешнего эффекта в тесте.

## Устройство app

Целевые пути ниже фиксируют место владения. Не создавать заранее пустые файлы и не дробить короткие модули. `mod.rs` может содержать и state, и методы владельца; `ui.rs` выделяется при реальном объёме.

```text
app/src/
  main.rs                     запуск eframe и платформенной интеграции
  app.rs                      shell, навигация, общие настройки, связь features
  jobs.rs                     локальный one-shot Job<T>
  features/
    recording/                RecordingController, форма target, состояние session/finalize
    capture/                  CaptureController, capture/screenshot jobs и overlay
    conversion/               ConversionController, probe/estimate/convert и UI
      controls.rs
    library/                  LibraryController, query/scan/removal и UI
      viewer.rs               загрузка и показ выбранного файла
      player.rs               воспроизведение, seek, audio/video sync
      hover_preview.rs
      thumbs.rs
  services/
    clipboard.rs              native clipboard worker
    settings_writer.rs        coalescing writer
  app/
    actions.rs                межфункциональные действия и page-shell adapters
    desktop.rs                open/reveal/rename и результаты этих операций
    recovery.rs               recovery owner и уведомления
    state.rs                  Page, Pending и общие app-типы
  pages/
    capture.rs, record.rs, audio.rs
    settings.rs, about.rs
  latest_worker.rs            bounded latest-request worker
  tray.rs, hotkeys.rs, i18n.rs  конкретные адаптеры приложения
```

Названия `Controller` означают владельца существующего состояния, а не ещё один слой над старым `*Ui`. При переносе поля и методы переезжают в него; прежняя владеющая структура удаляется или становится небольшим набором чисто визуальных полей. Не создавать зеркальные модели `ControllerState`, `ViewModel`, `Store` с одинаковыми значениями.

| Владелец | Что ему принадлежит | Что передаёт наружу |
|---|---|---|
| Recording | Выбранный target, состояние Idle/Starting/Recording/Saving, session, start/finalize handles, progress | Сохранённые пути, сообщения, намерение открыть библиотеку/скопировать файл |
| Capture | Ожидание скрытия окна, capture job, overlay selection, screenshot save/copy flow | Результат снимка и запрос изменения видимости окна |
| Conversion | Input/options, probe, estimate, conversion job, last output | Результат конвертации и обновлённые файлы |
| Library | Index/watcher/scan и смена каталога, query/hits, removal, viewer/previews/thumbnails | Open/reveal/rename/copy/convert действия и сообщения |
| App | Settings, текущая страница, native window/tray/hotkeys, перечисленные owners и общие services | Вызовы конкретных owners и команд eframe |

Не переносить все функции `app/*.rs` механически в services. Координация пользовательского сценария принадлежит соответствующему feature. OS-вызов принадлежит platform; app service нужен только для его фонового владения или очереди.

## Вызовы и данные

UI может непосредственно редактировать принадлежащие feature поля формы и создавать локальное действие, например `ConversionAction::Start`. Это не event sourcing: действие обрабатывается обычным `match` в том же update, без общего bus, регистрации обработчиков и сериализации команд.

Feature UI получает `&mut Feature`, доступные ему настройки/каталог и `&mut egui::Ui`. Он не принимает `&mut App`, не ищет другой feature через глобальный объект и не запускает поток из render-ветки. Дешёвый render-helper может получать несколько обычных ссылок; не вводить context-структуру ради каждой функции.

Межфункциональное действие обрабатывает App: `LibraryAction::Convert(path)` вызывает `conversion.set_input(path)` и меняет страницу. Завершённая запись возвращает пути; App обновляет библиотеку и выполняет after-completion действие. Для этого достаточно небольших локальных enum или результата метода. Общий AppCommand допускается для уже существующих единых UI/tray/hotkey входов записи/выхода; не расширять его до транспорта каждого изменения поля.

Один UI update делает три понятных шага: принимает внешние команды, опрашивает активных owners независимо от видимой страницы, затем рисует текущую страницу. Owners и их jobs живут всё время работы приложения. Переключение страницы не уничтожает конвертацию или финализатор.

## Фоновая работа

Использовать три существующих по смыслу формы работы, не универсальную async-платформу.

| Форма | Когда | Владение и завершение |
|---|---|---|
| One-shot `Job<T>` | Probe, load, scan, save, conversion, removal, open/reveal | Feature/service владеет handle и при необходимости cancel; возвращается один Result |
| `LatestWorker<Request>` | Повторяемый дорогой запрос, где старый результат теряет смысл: estimate, seek, hover | Один активный запрос, один заменяемый pending, generation у результатов |
| Session/service | Recording, clipboard, settings writer, OS stream, index writer | Собственный конкретный протокол start/stop/flush; bounded channels по назначению |

### Контракт Job<T>

- Основа — `JoinHandle<Result<T, E>>`, имя потока и только действительно необходимый cancel flag. Тип ошибки остаётся конкретным для потребителя или существующим `anyhow::Error`; не нужен новый каталог всех ошибок приложения.
- `poll` сначала проверяет `is_finished`, затем делает `join` и возвращает результат ровно один раз; panic превращается в понятную terminal error. `join` работающего потока на UI запрещён.
- Нельзя одновременно хранить такой же terminal result в receiver и глобальном completed-map. Progress и уведомления могут идти отдельно: это другие данные.
- Выставленный cancel — просьба остановиться, а не доказательство завершения. Если файл уже успешно опубликован, результат нельзя потерять из-за позднего cancel. Политику границы отмены определяет операция.
- Deadlines задаются конкретным владельцем для реального ожидания, а не автоматически всем jobs. Длительная конвертация не считается зависшей только по времени.
- UI должен повторно опрашивать pending job через request_repaint_after либо согласованный wakeup. Один repaint, запрошенный перед фактическим завершением потока, не гарантирует следующего poll.
- Drop helper не делает неограниченный join и не решает за владельца, можно ли бросить работу. Владелец критической операции удерживает её до результата/безопасного восстановления. Для одноразового read-only preview допустим явно выбранный detach с игнорированием позднего результата.

Начать с одного простого потребителя, затем второго. Если общий Job начинает требовать TaskKind, глобальный id, history, retry, registry и политику каждого feature, остановить его расширение: эти обязанности должны остаться в owners.

### Очереди и устаревшие результаты

Ограничить очередь там, где элементы велики или ввод может опередить обработку. Для terminal result нельзя молча использовать `try_send` с потерей сообщения. Для preview frame допустимо пропустить кадр, для результата сохранения — нет.

Generation применяется к изменяемому контексту: новый input, библиотечный каталог, seek. Проверки равенства generation/path защищают от реально возможных поздних результатов. Они не нужны в одноразовой операции с собственным каналом/handle, который уже однозначно относится к конкретному запросу.

LatestWorker не должен блокироваться на заполненной очереди старых результатов. При отмене или новом запросе он должен иметь возможность закончить отправку/отказаться от устаревшего результата. При panic/выходе worker UI получает ошибку и перестаёт показывать вечное ожидание. Не создавать неограниченное количество replacement workers, если native вызов не вернулся; bounded worker сам по себе не обеспечивает отмену блокирующего API.

## Запись, файлы и shutdown

Реальные защиты остаются возле ресурса: readiness/stop deadlines capture в media/platform, sync/atomic publish в файловой операции, memory estimate и concurrency у WebP scheduler. App не повторяет их глобальным таймером.

Ожидание остановки native capture выполняется фоновым координатором с общим deadline для всей группы. Для существующего JoinHandle достаточно периодической проверки `is_finished` и `join` завершившегося потока. Дополнительный watchdog-thread или новый terminal channel не нужны только ради ожидания результата. Истечение deadline не разрешает удалять файлы ещё работающего native worker.

Для записи остаётся явное состояние `Idle → Starting → Recording → Saving → Idle`. При ошибке сохраняются информация для UI и recovery files. Состояние `Saving` владеет finalizer handle до фактического завершения; пользовательское terminal event не означает автоматически, что поток уже закончил cleanup. `StopAction::Save` и `Discard` различаются, повторные команды обрабатываются идемпотентно на уровне владельца.

App начинает выход через конкретные методы owners и затем продолжает poll. Решения об exit и tray вычисляются, не хранятся второй изменяемой таблицей.

| Работа | Что означает выход |
|---|---|
| Recording start | Запросить cancel; если session успела создаться, корректно остановить её и завершить cleanup |
| Recording / finalization | Stop с Save; дождаться безопасного terminal result, сохранить recovery при отказе |
| Пользовательская conversion / screenshot save / removal / rename | Не потерять результат уже принятого изменения файла; завершить либо явно отменить там, где есть безопасный контракт |
| Recovery | Не прервать перенос исходников в неопределённом состоянии |
| Probe / estimate / viewer / catalog / housekeeping | Отменить или перестать ждать, если это не оставляет пользовательскую запись в работе; поздний результат не применять |
| Clipboard | Отдельно учитывать уже принятый copy и его bounded ожидание; busy не означает Saving, native timeout не доказывает отмену OS side effect |
| Settings | Сохранить последнюю версию, сообщить ошибку; оставить нынешний bounded flush |
| Перестраиваемые caches | Best-effort flush, потеря cache допускает rebuild; не блокировать выход неограниченно |

Эта таблица — целевой контракт перехода, включая устранение нынешнего detach для сохраняющего screenshot. При реализации его нужно закрепить тестом, а не считать текущий список в `App::quit` доказательством правильного поведения.

Tray отражает пользовательскую фазу записи/сохранения/обработки; условие «любой worker занят» для этого непригодно. `blocks_exit` и `tray_state` могут вычисляться из одного feature-state, но не должны быть одним флагом.

## Настройки и модели

Persisted settings хранят пользовательские предпочтения. Полный request для media собирается один раз перед start. Не хранить копию значения, которое всегда переписывается при построении request.

У записи FPS и output height принадлежат `RecordSettings`. Animation quality хранит только GIF colors/dither и WebP quality. Полные параметры анимационного энкодера содержат итоговые FPS/height и качество. Conversion владеет своими параметрами и не заимствует случайно текущий профиль записи.

WebP различает сохранённые предпочтения, выбранный режим записи и текущую попытку кодирования. Сохранённые checkbox preferences могут помнить отключённую настройку; не объявлять её недопустимым состоянием. Runtime mode выводится один раз. Fallback attempt задаётся явно как Direct или Segmented и не пересчитывается из исходного режима пользователя.

Существующие новые типы `SourcePath`, `OutputPath`, `MediaDir`, `WorkDir` допустимы на границах, где ошибка роли пути опасна. Они не доказывают существование файла или отсутствие коллизий. Не вводить newtype для каждого промежуточного PathBuf и не создавать compatibility aliases при удалении старого API.

## Библиотека и кэши

Источник пользовательских файлов — каталог. SQLite, thumbnail atlas и preview proxies перестраиваемы. Сохранять текущую storage model до корректного сравнения альтернатив; простота JSON сама по себе не окупает новый протокол полного сохранения и загрузки.

LibraryController владеет index, watcher, scan и reconciliation. Смена каталога отделяет старые результаты; события, пришедшие во время scan, применяются после snapshot либо иначе учитываются без потери. Версия index меняется при обновлении details; cached hits зависят от версии, query и limit.

Внутренний перенос владения не должен создавать второй изменяемый индекс или клонировать всю библиотеку на каждый кадр. Блокирующее I/O выполнять в фоне; если нынешнее применение большого snapshot вызывает hitch, измерить его и отдельно изменить batch/apply, сохранив порядок событий. Перенос кода из страницы в controller сам по себе не ускоряет его.

Removal имеет одну трассу запуска/завершения. Различие Selected и OlderThan остаётся в данных запроса; возраст перепроверяется перед bulk removal. Не создавать фиктивный `older=Week` для одиночного удаления. Частичные ошибки возвращаются с конкретными путями, успешно удалённые файлы не возвращаются в UI.

## Ошибки, fallback и оптимизации

Ошибка получает тип только если от него зависит действие: Cancelled, известная I/O-причина, ресурсное ограничение или permanent failure. Контекст и путь добавляются на границе ресурса; UI переводит итог в локализованное сообщение. Не классифицировать FFmpeg по подстроке `out of memory`, если upstream не даёт надёжного кода.

Retry существует, если следующая попытка меняет условие отказа. Постоянные ошибки формата/валидации не лечатся шестью одинаковыми попытками. Неизвестный сбой нельзя автоматически назвать постоянным: сначала подтвердить фактический fallback и провести failure-сценарии. Process abort при OOM не превращается в Result обычным catch_unwind.

WebP-планировщик имеет один набор scheduling parameters. Размер сегмента и concurrency используют согласованный расчёт. Динамический бюджет можно убрать только после доказательства этого инварианта, включая округление и retry split. Расчётная память и реальный RSS — разные величины.

Оптимизация должна иметь наблюдаемый эффект: stop-to-file latency, ready-gallery latency, frame time, RSS, размер кэша. Не превращать benchmark-параметры в пользовательские настройки. Не удалять полезный benchmark seam лишь потому, что его не вызывает GUI.

## Как LLM вносить изменение

1. Найти владельца пользовательского сценария и описать ожидаемое поведение, включая отмену/ошибку, если они затронуты.
2. Прочитать его состояние, ближайшие вызовы и тесты. Проверить факты памяти по коду; не считать старый plan выполненной реализацией.
3. Изменить конкретный owner и нижележащую операцию. Общий helper извлекать из реального повторения, не из гипотетического будущего.
4. Удалить прежнее поле/маршрут/обёртку в той же порции миграции. Не оставлять постоянных compatibility re-exports или два источника состояния.
5. Проверить реальные контракты: результат, ошибки, поздний ответ, повторный запуск, выход при активной работе. Не ограничиваться тестом внутреннего enum, если важен выбранный backend.
6. Для изменения поведения выполнить релевантные tests, затем обязательные проверки `CLAUDE.md`; не повторять уже успешный прогон неизменного кода. Для UI сохранить AccessKit labels, геометрию, темы, DPI и локализацию; реальные UI-проверки проводить только в изолированной копии.

Не добавлять DI container, общий event bus, async runtime, plugin architecture, универсальный repository, глобальный mutable state или новые крейты без конкретной задачи, которой не хватает нынешних механизмов. Не устанавливать лимит строк/файлов и не делать все модули искусственно одинаковыми.

## Завершение перехода

Переход завершён, когда feature UI не получает весь App, каждый пользовательский job имеет одного владельца, глобальный TaskSupervisor с completed history больше не нужен, настройки не дублируют effective значения, а приложение сохраняет прежние пользовательские сценарии. Перемещение файлов без этих результатов не считается архитектурным улучшением.

После перехода обновить этот статус и фактическую карту путей. До этого руководство описывает цель, а план — порядок её достижения; незавершённые этапы не выдаются за действующее устройство проекта.
