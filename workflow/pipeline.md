# Конвейер анализа и учёт работы в очереди — проект

Проект задач 11.1, 11.2 и 6.3 из [todos.md](todos.md). Что сейчас в работе — [process.md](process.md);
справочник — [dev-context.md](dev-context.md); темы — [topics.md](topics.md). Контракт для
подзадач: код пишется по нему, расхождения сначала правятся здесь.

## 0. Решения пользователя

* Каждая **логическая** стадия анализа — отдельная задача очереди (распознавание и диаризация —
  разные). Мелко не дробить: склейка тем — одна задача. Многосоставная работа — составная задача
  с подзадачами, которые видно в очереди («7 из 12»).
* Главное — **видимый ход**: прогресс, сколько идёт, примерно сколько осталось.
* Перезапуск только по клику: перезапуск стадии сбрасывает всё, что от неё зависит, и сразу ставит
  всю цепочку.
* **Частичное использование:** как только есть реплики, записью можно пользоваться — диалог и
  агент работают с тем, что готово; упала или отключена диаризация/индекс/темы — пропадают только
  их возможности.
* **Настройка анализа:** перед запуском пользователь выбирает стадии — диаризация (и сколько
  человек), темы, разбор тем; отключённое можно добавить позже из «⋯».
* Кнопки «Расшифровать заново» нет; вместо неё меню «⋯» в шапке «Диалога».
* В очереди видна **вся** работа моделей и инструментов: анализ записей, ответы в чате, шаги и
  инструменты агента — со статистикой (вызовы модели, токены, время). Служебные вызовы (проверка
  модели на «Моделях») — не задачи и в очереди не видны.
* История сделанного хранится 30 дней, старше удаляется сама.
* Разбор темы (6.3): раскрытие темы растягивает блок тем на всю высоту «Диалога»; решения, задачи,
  вопросы — разделами разбора, не отдельными блоками.

* Режим размышлений локальных моделей по умолчанию **выключен**, включается переключателем у
  модели в UI (3.9).
* Готовность стадий записи определяется по самим данным в её базе (реплики, чанки с
  эмбеддингами, главы, разделы разбора), а не отдельными отметками: уже распознанные записи
  работают без повторного анализа. `queue.db` пересоздаётся (история очереди пропадает).
* Коммит — один, когда весь список этапов (P1–P6, P4c) готов и проверен головой (разрешение
  пользователя от 2026-10-21 на эту серию работ).

## 1. Очередь (`mediaa_core::queue`, `queue.db`, схема 2 — без миграции)

```
tasks:      id, kind, title, input, priority, status, cursor, partial, result, progress, error,
            attempts, created_ms, updated_ms,
            parent        — составная задача (NULL у верхних),
            scope         — ключ записи (file id) или NULL: для блокировки и фильтра,
            inline        — 1: исполняет вызывающий (чат), воркер не берёт,
            started_ms, finished_ms,
            stats         — JSON: {model_calls, prompt_tokens, completion_tokens, model_ms, models: [..]},
            detail        — JSON для строк инструментов: {tool, args (кратко), result_chars}
task_deps:  task, needs                 — task ждёт needs (все needs — done)
kind_stats: kind, runs, ms, units       — для оценки времени; units — минуты записи или слова
```

* Статусы: `queued`, `running`, `paused`, `done`, `failed`, `cancelled` и `waiting` — у составной
  задачи (сама не исполняется).
* `claim` берёт `queued`, не `inline`, вид из своих обработчиков, **все зависимости `done`**,
  по приоритету и порядку.
* Составная задача: `running`, когда идёт хоть одна дочерняя; `done`, когда все дочерние `done`;
  `failed`, когда упала дочерняя (её ошибка видна у составной). Прогресс — по детям: среднее,
  взвешенное по оценке времени (§4).
* Задача, узнавшая, сколько будет работы (план тем, склейка), ставит дочерние **в той же
  транзакции**, в которой завершается (`complete_with(children)`), поэтому составная не может
  завершиться раньше времени.
* `pause`/`resume`/`cancel` составной действуют на всех её детей.
* `inline`-задачи: `begin_inline(kind, title, input, parent, scope)` → `running`;
  `finish(result)` / `fail(error)`. Если программа закрылась посреди — при старте такие
  становятся `cancelled` (воркер их не продолжает).
* История: `done`/`failed`/`cancelled` верхнего уровня старше 30 дней удаляются вместе с детьми
  (при старте воркера и раз в сутки); `kind_stats` остаётся. Кнопка «Очистить» — как сейчас.

## 2. Стадии анализа записи

Нажатие «Распознать» открывает настройку анализа (§3) и ставит составную **«Анализ: <файл>»**
(`analysis`, scope = file id) с выбранными стадиями и зависимостями (отключённая стадия не
ставится; зависящая от неё ждёт ближайшую включённую предыдущую):

| Вид | Что делает | Ждёт | Данные (база записи) | Сброс при перезапуске |
|---|---|---|---|---|
| `transcribe` | VAD + распознавание | — | реплики, слова | всё содержимое расшифровки |
| `diarize` | говорящие (если выбрана модель; ошибка — реплики без говорящих, задача `done` с предупреждением) | `transcribe` | говорящие реплик, `meta.diarized` | говорящие, имена говорящих |
| `index` | чанки, FTS, эмбеддинги | `diarize` или `transcribe` | `chunks` | чанки и эмбеддинги |
| `topics` (составная) | — | `index` | — | — |
| ├ `topics-plan` | границы тем (план в `meta.outline-plan`); ставит `topic-digest` × N и `topics-merge` | — | `outline-plan`, заготовки глав | главы, ключи `outline-*` |
| ├ `topic-digest` × N | сводка темы N (окна длинной темы — внутри) | — | глава N | — |
| └ `topics-merge` | склейка (одна задача, решения в её журнале); ставит составную `details` | все `topic-digest` | главы, `outline-topics`, `outline-merge` | — |
| `details` (составная) | — | — | — | разделы разбора |
| └ `topic-detail` × M | разбор темы M (6.3) | — | `Digest.sections` главы M | — |

* Каждая задача читает вход из базы записи, а не из памяти другой задачи: любая стадия
  перезапускается отдельно и продолжается после перезапуска программы (курсоры — как сейчас).
* Тема, которую пользователь раскрыл, а её `topic-detail` ещё в очереди, получает высокий
  приоритет.
* Стадии и их сброс — одна таблица в коде (`agent::pipeline`): порядок стадий, вид задачи,
  функция сброса данных. Перезапуск и UI берут всё из неё.

## 3. Настройка, перезапуск и доступность записи

* **Настройка анализа** (окно при «Распознать»): распознавание — всегда; «Говорящие
  (диаризация)» и поле «сколько человек» (пусто — определить самим; → `Input.speakers`);
  «Индекс для поиска»; «Темы» (нужен индекс); «Разбор тем» (нужны темы) — флажки; зависимые
  флажки гаснут вместе с тем, от чего зависят. Выбор запоминается в настройках как значение по
  умолчанию для следующего раза. Диаризация без выбранной модели — флажок недоступен с
  подсказкой.
* Меню «⋯» в шапке «Диалога»: «Анализировать заново…» (то же окно настройки), «Заново:
  распознавание», «Заново: говорящие…» (поле «сколько человек»), «Заново: индекс», «Заново:
  темы», «Заново: разбор тем»; для стадий, которых у записи нет, — «Добавить: …». Пока идёт
  анализ записи — «Остановить» и недоступные перезапуски (одна перестройка на запись).
* Перезапуск стадии X: подтверждение «Будут пересобраны: X, …, разбор тем» → в одной транзакции
  незавершённые задачи анализа этой записи → `cancelled` (идущая останавливается на ближайшей
  контрольной точке); данные стадий ≥ X сбрасываются; ставится **новая** составная «Анализ» с
  задачами стадий ≥ X (прежний анализ остаётся в истории).
* **Доступность — по готовым данным, не по анализу целиком:**
  * нет реплик (распознавание не готово или перестраивается) — запись недоступна: в «Диалоге»
    только ход анализа, чат закрыт, поиск по папке её пропускает;
  * реплики есть — диалог и чат работают; каждая возможность появляется, когда готова её стадия,
    и пропадает на время её перестройки: говорящие (диаризация), поиск по смыслу (индекс), блок
    тем и шкала тем (темы), разбор (разбор тем);
  * упавшая или отключённая стадия — её возможности просто отсутствуют; в ходе анализа — ошибка и
    «Повторить», в «⋯» — «Заново/Добавить».
* **Агент по готовым данным:** набор инструментов и текст системного промпта (шаблоны) — по тому,
  что есть у записи: без индекса нет поиска по смыслу (остаётся чтение реплик и полнотекстовый
  поиск, если он есть), без говорящих — инструментов имён говорящих, без тем — карты тем.
  Готовность стадий — по самим данным записи (§0), без отдельных отметок.
* Ход анализа в «Диалоге» при доступной записи — компактной строкой над блоком тем («Анализ:
  темы 3 из 7, ≈ осталось 4 мин», раскрывается в стадии), в той же геометрии.

## 4. Время

* У задачи: `started_ms` (первый запуск), `finished_ms`; «идёт m:ss» — по ним.
* Остаток идущей: `elapsed · (1 − p) / p`, когда прогресс `p ≥ 5 %` и прошло ≥ 10 с; иначе — по
  истории.
* По истории: `kind_stats` — среднее время на единицу работы вида (минута записи для
  `transcribe/diarize/index`, тысяча слов для `topic-digest/topic-detail`, тема для
  `topics-merge`); до первого прогона вида — без оценки («оценка после первого прогона»).
* Составная и «Анализ»: сумма остатков детей + оценка стадий, которых ещё нет (по `kind_stats` и
  длине записи). Показывается «≈ осталось N мин» (округление до минуты, меньше минуты — «< 1 мин»).

## 5. Учёт работы моделей и инструментов (11.2)

* **`Scope`** (`mediaa_agent::scope`) — «работа в рамках задачи»: id задачи, соединение с очередью.
  `Scope::engine()` даёт обёртку `Engine`, которая на каждый вызов `chat/embeddings/rerank/
  recognize/diarize` прибавляет к `stats` задачи: вызов, токены (`ChatAnswer.usage`), время,
  модель. Вызовы провайдеров (`assistant::provider`) пишут так же, токены — из ответа.
* Код агента получает **только `Scope`**, не голый `Engine` (проверяется компилятором): работа
  мимо очереди невозможна. Голый `Engine` остаётся у служебного кода приложения (проверка и
  скачивание моделей на «Моделях», статус движка) — это не задачи.
* **Ответ в чате** — inline-составная «Ответ: <начало вопроса>» (scope = запись или папка):
  * шаг модели — дочерняя `model-step` (статистика вызова);
  * инструмент — дочерняя `tool` с `detail`: имя, краткие аргументы, объём результата; вызовы
    моделей внутри инструмента (эмбеддинги, реранк, суб-агент) — в его `stats`;
  * отмена ответа — задача `cancelled`.
* Фоновые задачи вызовы моделей не дробят на строки: в их `stats` — число вызовов, токены, время.

## 6. Интерфейс

* **«Очередь»:** дерево (верхние задачи, раскрытие — дети); строка: значок статуса, название,
  полоса прогресса, «идёт m:ss» / длительность, «≈ осталось», у составной «7 из 12»; справа —
  вызовы модели, токены вход/выход, модель (у инструмента — имя и аргументы); ошибка текстом.
  Фильтр: всё / анализ записей / чат; по записи. Действия как сейчас (пауза, продолжить,
  отменить), для составной — на всё поддерево. Геометрия строк не прыгает (dev-context, «Основа
  дизайна»).
* **Студия, «Диалог»:** пока реплик нет — вместо реплик ход анализа: стадии строками
  (✓ готово / идёт: прогресс, «идёт m:ss», «≈ осталось» / ждёт / выключено / ошибка +
  «Повторить»), сверху итог «Анализ: ≈ осталось N мин»; когда реплики есть — компактная строка
  хода над блоком тем (§3). Геометрия строк — как у блока тем.
* **Окно настройки анализа** — §3.
* **Меню «⋯»** — §3; иконка в шапке «Диалога» на месте нынешней «Расшифровать заново».
* **Разбор темы (6.3):** раскрытие темы растягивает блок тем на всю высоту «Диалога»: закреплённая
  шапка (время, название, «‹ ›», свернуть/Esc), ниже разбор с прокруткой — разделы, пункты, время
  у пункта — кнопка (плеер туда, разбор открыт), выдержки в конце; пока не готово — «Разбор
  готовится…» и краткая сводка. Подсказка «Сводка» у стрелки убирается.

## 7. Разбор темы — данные и задача (6.3)

* `Digest.sections: Vec<Section { title, kind: List|Steps|Text, items: Vec<Item { text, time: Option<f64> }> }>`
  (`serde(default)`); время пункта проверяется по репликам, как у выдержек.
* `topic-detail`: тема в одно окно — один вызов; длиннее — пункты по окнам, затем сборка разделов
  из пунктов (без повторного чтения текста). JSON по грамматике.
* Промпты (`prompts/outline/detail*.j2`) пишет голова; исполнитель подключает шаблоны с текстом-
  заглушкой.

## 8. Этапы и исполнители

| Этап | Что | Исполнитель |
|---|---|---|
| P1 | Очередь: схема 2, родитель, зависимости, inline, статистика, время, история 30 дней, `complete_with`; тесты | DeepSeek |
| P2 | `agent::scope` (обёртка движка с учётом, §5) и перевод на неё фоновых задач; `agent::pipeline`: стадии, выбор стадий, сброс, готовность по данным, «Анализ» как составная; `transcribe`/`diarize`/`index` раздельно; запуск из студии | DeepSeek |
| P3 | Темы на подзадачах: `topics-plan`, `topic-digest`, `topics-merge`; `details` и `topic-detail` с заглушками промптов | DeepSeek |
| P3a | Тексты промптов разбора, точные тесты | голова |
| P4 | Учёт в чате (на `Scope` из P2): провайдеры; ответ в чате — inline-задача, поток событий (шаги с заголовками, размышления, куски ответа, ожидание слота/загрузка, стоп), сохранение в `messages.details`, мгновенный стоп (todos 7.4); режим размышлений: переключатель у модели, «ленивая» грамматика `<think>` перед JSON у локальных, reasoning у провайдеров (todos 3.9) | Sonnet (затрагивает цикл агента) |
| P4c | Чат: лента шагов вниз, размышления живьём, честное ожидание, «Шаги и размышления» у старых ответов (7.4); название чата моделью «Заголовки», один раз и без ручного переименования; вкладки без подсказки (7.5, шаблон — голова) | DeepSeek |
| P4a | Агент по готовым данным: инструменты и системный промпт по готовым данным записи (тексты шаблонов — голова) | Sonnet |
| P5 | Интерфейс: очередь деревом со статистикой; окно настройки анализа; ход анализа и «⋯» в студии; доступность по готовым данным; режим чтения разбора | DeepSeek |
| P6 | Живая проверка на 27-минутном видео: весь ход, оценки времени, перезапуск каждой стадии, чат в очереди, разбор тем | голова |

P1 → P2 → (P3 ∥ P4) → P4c → P5 → P6. P2 делает `Scope`, на нём стоят и P3 (темы, `outline.rs`), и P4 (цикл агента, `assistant/*`, чат) — у них разные файлы, поэтому параллельно. Мелкие правки не запускаются отдельным исполнителем — входят в ближайший этап по тем же файлам.
