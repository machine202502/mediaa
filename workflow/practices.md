# Практики работы с проектом

Файл содержит проверенные подходы к решению повторяющихся задач. Модель может дополнять,
переписывать и очищать его, если практика устарела. Практики помогают принимать решения, но
уступают явному указанию пользователя, [CLAUDE.md](../CLAUDE.md) и [rules.md](rules.md).

## Проверка UI в отдельной копии

1. Создать отдельную тестовую библиотеку, не указывая на пользовательскую `Documents/MediaA`.
2. Задать уникальные `MEDIAA_DEV_LIBRARY` и `MEDIAA_INSTANCE_ID`.
3. Запустить собственную копию с нужной страницей через `--page=`.
4. Сохранить PID запущенного процесса и делать снимок только окна с этим PID через пример
   `mediaa-platform/examples/snap.rs`.
5. Проверить нужные состояния интерфейса и завершить только собственный процесс.
6. Если снимок не соответствует процессу, остановиться и не переключаться на поиск окна по
   заголовку: существует риск задеть пользовательский экземпляр.

## Локальная проверка изменений

- Для Rust сначала использовать быстрый
  `cargo check --workspace --lib --bins --profile dev-check`, затем targeted tests
  затронутого крейта.
- Перед завершением запускать полный набор из `CLAUDE.md`.
- Для UI-изменений проверять не только данные и тесты, но и стабильность компоновки по снимкам
  нужных страниц в отдельной копии.

## UI/UX-регрессия с `egui_kittest`

- Запускать настоящие egui-экраны через `egui_kittest::Harness`, а не дублировать UI в тестовых
  mock-виджетах.
- Создавать `App` через test-only фабрику с `TestCatalog`: временная библиотека, фиксированные
  дисплеи, окна, микрофоны и отключённые native-сервисы.
- Искать и нажимать элементы через `kittest` и AccessKit. Для недоступного по координатам
  элемента использовать `click_accesskit`, а не управлять реальным окном.
- Для визуальной регрессии использовать `Harness::snapshot` с `OperatingSystem::Windows`,
  фиксированными размером и dark theme. Baseline хранить в `crates/app/tests/snapshots`.
- Обновлять baseline только командой
  `UPDATE_SNAPSHOTS=true cargo test -p mediaa --lib ui_regression_snapshot`.
- Общие поведенческие тесты выполнять на всех платформах. Pixel snapshots запускать на Windows,
  чтобы различия системных шрифтов и GPU не скрывали реальные изменения ослабленными порогами.
- Не сравнивать большие страницы с движущимися индикаторами и hover-состояниями. Снимок должен
  изображать конкретное устойчивое состояние.
- Если один тест создаёт несколько `Harness`, делать не более одного snapshot на тест либо
  объединять `SnapshotResults`; независимые harness не должны молча терять результат.
- Реальные `RecordingSession` внутри одного test binary запускать последовательно через общий
  mutex: параллельные FFmpeg-сессии приводят к нестабильному аварийному завершению процесса.
- Locale `rust-i18n` глобальный. App UI tests держат общий mutex на время жизни `Harness`;
  перед созданием второго harness в том же тесте первый нужно явно удалить.

## Работа с долгосрочной памятью

- Новый проверенный подводный камень записывать в `stones.md`, а повторяемый способ решения — в
  `practices.md`.
- Не превращать разовое наблюдение или теоретическую возможность в устойчивую практику.
- При устаревании удалять или исправлять запись, а не сохранять противоречивые варианты.
- Практику переносить в `rules.md` только по явному указанию пользователя.
