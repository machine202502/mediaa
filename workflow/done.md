### 2026-10-25 — статические участки WebP и компактные уведомления

* По журналу `mediaa.log` ошибка `part-000076.webp has no VP8X chunk` возникала не из-за
  повреждения MKV или отсутствия итогового файла. `libwebp_anim` для неподвижного временного
  участка записывает обычный статический WebP без контейнера `VP8X/ANIM/ANMF`; сегментатор
  принимал это за недописанный файл. После шести попыток сработал линейный fallback, поэтому
  итоговый WebP был получен.
* Перед проверкой сегмента статический WebP теперь штатно оборачивается в один кадр animated
  WebP с длительностью исходного сегмента. Уже анимированные части не переписываются. Это
  применяется и к live-чанкам во время записи, и к сегментной конвертации после неё.
* Вся WebP-запись получает единый `webp-…` ID. С этим ID в журнал пишутся выбранный маршрут,
  состояние live-кодировщика, запуск сегментного кодирования, шаги деградации, линейный fallback,
  финальный результат и полная ошибка. Один поиск по ID показывает всю цепочку.
* Визуально сохранён прежний компактный toast: тёмная плашка, цветная иконка, короткий текст,
  стрелка и крестик. Собственная обёртка используется только для раскрытия: полный технический
  текст не обрезается и показывается внутри той же плашки с прокруткой.
* ID лога и список исходников показываются только после раскрытия. ID и кнопка «Копировать»
  копируют цепочку логов; каждый MKV показан отдельной строкой с кнопками «Копировать ссылку»
  и «Показать файл». Дополнительно можно скопировать ссылки сразу на все исходники.
* Поведение прежнее: обычные уведомления исчезают по таймеру, раскрытая плашка остаётся, пауза
  наведения продлевает показ.
* Проверка: статический участок реально закодирован FFmpeg и успешно собран сегментатором;
  раскрытие полного текста проверено UI-тестом, свёрнутое и раскрытое состояния проверены
  рендером PNG; `cargo test --offline --workspace` — 216 тестов;
  `cargo clippy --offline --workspace --all-targets` — без предупреждений.
* Изменение остаётся локальным, коммит не запрошен.

### 2026-10-25 — WebP во время записи и каскадный откат

* В настройки записи добавлены независимые «Сегментированный WebP» и «Параллельное
  кодирование во время записи», обе включены по умолчанию. Они показываются только для WebP;
  без сегментации параллельный переключатель остаётся на месте, но неактивен и не сбрасывает
  выбранное значение.
* Маршруты разделены явно: GIF и видео идут через один `video-N.mkv`; WebP без сегментации —
  прямо через FFmpeg; WebP с сегментацией без параллельности — через бюджетный planner с одним
  воркером; оба переключателя — через live-кодирование во время записи.
* Live-WebP пишет исходник секундными MKV-чанками с ключевым кадром раз в секунду. Закрытые
  чанки сразу кодируются фоновым пулом; число воркеров учитывает реальный размер источника, CPU
  и бюджет памяти. Каждый live-воркер внутри FFmpeg ограничен одним потоком, чтобы внешняя
  параллельность не умножалась на внутреннюю. Текущий ещё открытый чанк не отдаётся кодировщику
  до остановки записи.
* При остановке готовые части собираются в один animated WebP без повторного кодирования.
  Отмена финализации также останавливает ожидающую очередь live-кодировщика.
* Отказы идут по цепочке `live WebP → WebP после записи → линейный FFmpeg → исходный MKV`.
  Ошибка live-кодирования не останавливает захват. При финальной ошибке пользователь получает
  ссылки на все сохранённые MKV-чанки; при успешной склейке — на один исходный MKV.
* Для live-склейки интерфейс показывает спиннер с таймером; измеряемые проценты остаются только
  у сегментной конвертации после записи.
* Проверка: `cargo test --offline --workspace` — 209 тестов; live-WebP-сценарий без отката
  прогнан пять раз подряд; отдельно проверены принудительный запуск после отказа live-кодера,
  склейка MKV, отмена, сохранение нескольких исходных чанков и маршруты GIF/WebP.
  `cargo clippy --offline --workspace --all-targets` — без предупреждений.
* Изменение остаётся локальным, коммит не запрошен; ждёт проверки пользователя.

### 2026-10-25 — независимый крейт WebP-планировщика

* Бюджет, план сегментов, пул воркеров, ретраи, адаптивная деградация, проверка
  временных WebP и RIFF-склейка вынесены в `mediaa-webp-pipeline`.
* Крейт не зависит от FFmpeg, `mediaa-core` и приложения. Кодирование передаётся через
  интерфейс `SegmentBackend`, поэтому его можно тестировать с fake backend без статического
  FFmpeg и независимо заменять реализацию.
* Конфигурация доступна через `PipelineTuning`: бюджет, максимум воркеров, число попыток,
  минимум/максимум кадров, фиксированная память энкодера и задержка повтора.
  `RunReport` возвращает число сегментов, попытки, пиковый резерв памяти и шаги деградации.
* В `mediaa-media` остался адаптер `FfmpegSegmentBackend`: он только кодирует один сегмент
  через FFmpeg/libwebp. Планировщик больше не знает о FFmpeg, а media не знает деталей
  бюджета и повторов.
* Добавлены независимые тесты публичного API, планирования, бюджета, transient/permanent
  ошибок, отмены, битого сегмента, склейки и отчёта выполнения.
* Повторный release-замер после выноса: 19,324 с, 31 730 870 байт, 1152×720, 31,603 с;
  прежний результат не ухудшился.
* Проверка: `cargo test --workspace` — 199 тестов; `cargo clippy --workspace --all-targets` —
  без предупреждений.
* Изменение остаётся локальным, коммит не запрошен.

### 2026-10-25 — бюджетная сегментация WebP-записи

* Сегментный WebP подключён только к финализации записи с экрана/региона. Обычная
  конвертация WebP и все GIF-пути остаются прямыми через FFmpeg.
* По умолчанию доступно 512 МБ бюджета и не более 8 воркеров. Стартовое число воркеров
  выбирается по разрешению, качеству, длине сегмента, CPU и оставшемуся бюджету.
* Каждый сегмент резервирует расчётную память из общего бюджета. При ошибке памяти
  параллельность и максимальная длина незавершённых сегментов уменьшаются вдвое,
  после чего повторяются только незавершённые части. Quality, fps и method не меняются.
* Каждый сегментный декодер H.264 ограничен одним потоком, иначе параллельные FFmpeg-задачи
  создавали слишком много декодеров и исчерпывали память ещё до WebP-энкодера.
* Каждый готовый временный WebP проверяется на `VP8X`, `ANIM` и наличие кадров. Пустой
  или частичный файл после аварийной остановки не считается успешным сегментом.
* Замер на `Recording_2026-10-25_06-26-23.mkv` при 1152×720, 60 fps, WebP quality 80:
  прямой путь 57,754 с и 30 110 398 байт; сегментный — 19,291 с и 31 730 870 байт.
  Ускорение примерно в 3 раза, размер больше на 5,4 %, длительность отличается на 0,07 с.
* Стресс в отдельном процессе с Windows Job Object подтвердил реальные системные ошибки
  памяти и шаги `8 → 4 → 2 → 1` воркер, `60 → 30 → 15 → 7 → 3 → 1` кадр. При 256–640 МБ
  процесс завершился управляемой ошибкой без краха, при 768 МБ обработка успешна за 15,592 с.
* В худшем случае с одним очень коротким сегментом время может стать хуже прямого пути
  из-за накладных расходов FFmpeg, но качество остаётся прежним, а система не теряет
  управляемость. Исходный MKV в этом случае сохраняется существующим механизмом восстановления.
* Проверка: `cargo test --workspace` — 193 теста; `cargo clippy --workspace --all-targets` —
  без предупреждений.
* Изменение остаётся локальным, коммит не запрошен.

### 2026-10-25 — стратегии кодирования GIF/WebP

* Добавлен общий интерфейс `AnimationEncoder`: backend получает входной файл, окно
  для оценки размера, формат, настройки анимации, уровень сжатия и признак
  «конвертация/финализация записи». Текущий `FfmpegAnimationEncoder` реализует
  существующий прямой путь через `palettegen`/`libwebp_anim`.
* Конвертация и финализация GIF/WebP-записи больше не содержат собственные ветки
  кодирования: обе проходят через `animation::encode`. Будущий сегментированный
  или другой backend подключается выбором в `animation::backend(format, origin)`.
  Полностью live-запись дополнительно потребует абстракции источника кадров, но
  интерфейс финального кодирования и UI останутся прежними.
* Backend сам сообщает `None` или измеряемый прогресс, поэтому будущая сегментная
  реализация сможет вернуть настоящие проценты без изменений страницы конвертации.
  Общая обёртка также удаляет частичный выходной файл при ошибке backend.
* Декодирование уже готового animated WebP вынесено в тот же модуль и переиспользуется
  обоими путями.
* Проверка: выбор backend для GIF/WebP, подключение пользовательской реализации,
  удаление частичного файла и оба формата через FFmpeg;
  `cargo test --workspace` — 188 тестов, `cargo clippy --workspace --all-targets` —

* Коммит: `fe30119`.

### 2026-10-25 — прямой WebP, восстановление MKV и качественные пресеты

* Параллельная сегментация WebP удалена после ошибки нехватки памяти. FFmpeg/libwebp снова
  кодирует один поток напрямую; для WebP остаётся спиннер с таймером, без фиктивных процентов.
* Если финальное сохранение видео или анимации не удалось, исходные MKV переносятся в папку
  библиотеки с суффиксом `(source)` и не удаляются вместе с рабочей папкой. При ошибке копирования
